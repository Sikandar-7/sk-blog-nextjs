This blog used to be a Next.js frontend on a headless WordPress backend. I
rebuilt it on Astro. Before doing that I wanted a number, not a slogan, so
here is what I actually measured.

## What "ships less JavaScript" means

Next.js renders with React, and React runs in the browser. Even a page that is
pure text needs the framework shipped, parsed and hydrated before it is
interactive. In my food delivery app, the Next.js build reports it plainly:

```
+ First Load JS shared by all    87.1 kB
```

That is the floor. Every page pays it, including a page with nothing to click.

Astro renders components to HTML at build time and ships no JavaScript unless
you ask for it. Interactive pieces are opt-in "islands". An article has
nothing to hydrate, so it gets nothing.

After the rebuild I checked what an article page actually references:

```bash
$ grep -oE '<script[^>]*src="[^"]*"' dist/blog/why-your-backend-died/index.html
  /_astro/page.BraL6W9_.js     # 4.0K
```

**4 KB**, and that is Astro's link-prefetcher, not a framework. The React
runtime is not in the page because nothing on it needs React.

## The part people get wrong

The interesting bit is what happens when you *do* need interactivity. This
blog has comments, and comments need JavaScript.

If I had put them in the page, the saving would evaporate. Instead:

```astro
<Comments slug={post.id} client:visible />
```

`client:visible` means the component downloads when the reader scrolls to it.
Someone who reads half the article and leaves never downloads the comment code
at all.

You can see the split in the build:

| Page | JavaScript up front |
| --- | --- |
| Article | ~12 KB |
| `/write` (the editor) | 76 KB, loaded only there |

The editor pulls in a markdown parser and a sanitiser. That is fine — it is an
authoring tool for a handful of people. What matters is that a reader never
pays for it. In the Next.js version, shared chunks meant everyone paid a bit
of everything.

I also swapped React for Preact for the islands, which took the interactive
runtime from about 188 KB to roughly 3 KB. For a comment box and a login form,
React's ecosystem buys nothing.

## So is Astro better?

For this blog, yes. Generally, no — they are built for different jobs.

**Astro is better when** the page is mostly content: blogs, docs, marketing
pages, landing pages. Its default of "no JavaScript" is exactly right there.

**Next.js is better when** the page is mostly application: dashboards,
multi-step flows, anything with heavy client state. Fighting Astro to build an
app is worse than accepting React's baseline, and Next has far more ecosystem
and far more jobs attached to it.

There is also an honest caveat: **a well-built static Next.js blog is also
fast.** The largest performance factor is not the framework, it is whether
pages are pre-rendered or assembled per request. A static Next.js site beats a
database-backed Astro site every time. The framework is the second decision,
not the first.

## What actually made it fast

Ranked by how much they mattered:

1. **Static output.** HTML built ahead of time and served from a CDN. Nothing
   waits on a database. This is most of the win, and you can get it in either
   framework.
2. **Not shipping the framework.** Astro's contribution, and it is real —
   about 83 KB per page here.
3. **Self-hosted fonts.** `@fontsource-variable` instead of Google Fonts
   removes a DNS lookup, a TLS handshake and a request to a third party.
4. **Lazy islands.** Comments cost nothing until someone scrolls to them.

If you only do the first one, you have already taken the biggest step. The
rest is refinement — worthwhile refinement, and measurable, but do not skip
straight to arguing about frameworks.

## How to check your own site

Do not take my numbers. Build it and look:

```bash
npm run build
grep -oE '<script[^>]*src="[^"]*"' dist/your/page/index.html
du -h dist/_astro/*.js
```

The number that matters is what a reader downloads before they can read.
Everything else is a preference.
