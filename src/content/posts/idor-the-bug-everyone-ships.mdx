Here is a route that looks completely reasonable:

```ts
router.get('/orders/:id', authMiddleware, async (req, res) => {
  const order = await prisma.order.findUnique({
    where: { id: req.params.id },
  })
  if (!order) return res.status(404).json({ message: 'Not found' })
  return res.json({ data: order })
})
```

There is `authMiddleware`. You must be logged in. Ship it?

No. Any logged-in user can read **any** order — including the customer's name,
phone number and home address — just by changing the id in the URL.

This is **IDOR**: Insecure Direct Object Reference.

## Authentication is not authorisation

- **Authentication** answers *who are you?*
- **Authorisation** answers *are you allowed to touch this specific row?*

`authMiddleware` only does the first one. The second check is the one people
forget, because in testing you only ever open your own records.

## The fix

Compare the row's owner against the caller:

```ts
const u = req.user!
let allowed =
  u.role === 'SUPER_ADMIN' ||
  order.customerId === u.id ||
  order.restaurant.ownerId === u.id

if (!allowed) {
  return res.status(403).json({ message: 'No access to this order' })
}
```

## The variant people miss

Role checks feel safe, so this looks fine:

```ts
router.put('/orders/:id/status', roleGuard('RESTAURANT_OWNER'), handler)
```

But *which* restaurant owner? Without a second check, owner A can mark owner
B's orders as delivered. A role gate is not a tenancy gate.

## How to find it in your own code

Go through every route with an `:id` and ask one question: **does this compare
the record to the caller?** If the only guard is "is logged in" or "has role",
you have found one.

Try it on your own project. Log in as a normal user, open something that
belongs to you, then change the id by one. If you can see someone else's data,
so can everyone else.
