Every developer with a few side projects has hit this: you open a demo you
built months ago, and it loads — but everything is empty. The frontend is fine.
The backend is gone.

I hit it twice in one week. Here is what went wrong and what I changed.

## The two ways it happens

**Free tiers pause.** Supabase pauses a free project after about a week of
inactivity. The domain still resolves, the connection still opens, and then you
get a `tenant not found` error that looks nothing like "your database is
asleep".

**Free hosts vanish.** A WordPress install on a free host disappeared entirely.
The domain still served nginx — just a `404` where the REST API used to be. The
frontend kept rendering its empty state forever.

## Why it is worse than it looks

A dead backend on a portfolio project is not just a broken demo. It is a broken
demo that a potential client might open. The site looks polished, loads fast,
and shows nothing. That reads as "abandoned", not "the free tier paused".

## What actually fixes it

### 1. Render content statically

If your posts, products, or listings can be baked into HTML at build time, do
it. A static page cannot lose its database — the data is already in the HTML.

```bash
# The content is fetched once, at build, not per request
npm run build
```

Reads become CDN-fast as a side effect. The database only gets touched when
someone writes.

### 2. Always ship a fallback

If a fetch fails, render something reasonable instead of nothing:

```ts
try {
  const res = await api.get('/restaurants')
  setItems(res.data.data.length ? res.data.data : fallbackItems)
} catch {
  setItems(fallbackItems)
}
```

An empty section reads as broken. A populated one reads as fine — and buys you
time to notice.

### 3. Separate "down" from "empty"

Your empty state should not be the same as your error state. "No posts yet"
and "we could not reach the server" are different problems, and only one of
them is your fault.

## The uncomfortable lesson

The projects that survive are not the clever ones. They are the ones with the
fewest moving parts that can independently disappear.

Before you add a service, ask what your site looks like the day that service
stops answering. If the answer is "blank", you have just added a way to fail.
